# IdentityPrvd — Беклог покращень

Ідеї для розвитку бібліотеки. Не пріоритезовано, але покриває як обов’язкові enterprise-фічі, так і UX-покращення.

- [ ] Додати PKCE та стандартні OAuth 2.1 флоу (authorization code/implicit/device), щоб клієнти могли працювати не лише через кастомні `/signin`.
- [ ] Запровадити адаптивну MFA: політики ризику (локація, пристрій, IP) + API для їх конфігурації й відображення стану на клієнті.
- [ ] Розширити керування сесіями: адмінські ендпоінти для інспекції сесій усіх користувачів, ревокації та webhook подій.
- [ ] Вбудувати audit trail: журнал логінів/змін безпеки з API для пошуку, це must-have для enterprise.
- [ ] Додати rate limits/CAPTCHA hooks на чутливі маршрути (signin/signup/reset) з тонкими налаштуваннями.
- [ ] Окремий ендпоінт політики паролів: повертає правила складності, історії, заборонених шаблонів + можливість оновлення на льоту.
- [ ] Альтернативні сценарії відновлення: підтвердження через довірений пристрій чи контакт, а не тільки код/MFA.
- [ ] Масові адмін-операції: імпорт/експорт користувачів, пакетне призначення ролей/клієнтів із прев’ю та валідацією.
- [ ] Ротація секретів клієнтів: ендпоінти для попередньої генерації другого секрету, планового вимкнення старого, аудиту використань.
- [ ] Сумісність зі SCIM 2.0 для інтеграції з корпоративними каталогами (Azure AD/Okta) та синхронізації користувачів/груп.
- [ ] Раціоналізувати ендпоінти: наприклад, об’єднати `signin`/`signin-passwordless` через параметр `mode`, `devices/unverify` з `delete` через `PATCH`.
- [ ] Webhook/Event API: транслювати события signup/confirm/change-password/MFA у зовнішні сервіси.
- [ ] UI metadata endpoint: повертає локалізовані тексти, політики, банери для white-label клієнтів.
- [ ] Розширити passwordless WebAuthn/FIDO2 для апаратних ключів і стандартизувати DTO.
- [ ] Додати контекстні бани: ендпоінти для тимчасових/постійних блокувань користувачів або клієнтів з причинами, інтеграція у `SigninService`.
- [ ] Self-service exports: ендпоінт для вивантаження користувачем власних даних (GDPR).
- [ ] Виділити окрему адмін-фічу: ізольовані маршрути `/api/admin/*`, окремі scopes, RBAC та аудит для керування ролями/клеймами/клієнтами, щоб спростити делегування адміністраторам.
- [ ] Перепланувати існуючі ендпоінти, щоб вони відповідали REST та не дублювали логіку:
  - [x] `POST /api/identity/signin` приймає `"mode": "password|passwordless|mfa"` замість окремих маршрутів; повертає єдину відповідь. `GET /signin/challenge` підказує доступні фактори і замінює `signin-user-options`.
  - [x] Відновлення пароля стає ресурсом `POST /restore-password` (створює запит, повертає `verifyId`) та `PATCH /restore-password/{verifyId}` (встановлює новий пароль). Журнали бачать весь життєвий цикл.
  - [x] Пристрої: `PATCH /devices/{id}` з полем `verified` замінює `POST /devices/unverify/{id}`. Також варто додати `PUT /devices/{id}` для оновлення метаданих без повторної верифікації.
  - [x] Зовнішня авторизація і прив'язка об'єднуються в `/signin-external?purpose=login|link`, callback читає `purpose` і виконує відповідну гілку; немає дубльованих DTO.
  - [x] `DELETE /sessions/current` та `DELETE /sessions` (з `everywhere=true`) замінюють `signout`, `POST /sessions/revoke` приймає масив id у тілі замість безіменного DELETE з body.
  - [ ] Адмінські сутності отримують парність операцій: `GET /roles/{id}` та `GET /clients/{id}` повертають повний стан для форм редагування, `PUT /roles/{id}/claims`/`PATCH /roles/{id}/claims` дозволяють або замінювати, або точково додавати/прибирати зв’язки.
